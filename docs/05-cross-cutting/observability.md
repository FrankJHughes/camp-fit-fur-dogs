# Observability

Observability in the Camp Fit Fur Dogs platform provides correlation, request tracing, structured diagnostics, and measurable runtime signals across **all layers** of the system.  
It is powered by **Frank.Core’s observability engine**, while each product layer (API, Application, Infrastructure) emits its own domain‑specific events.

This document explains the cross‑cutting observability model and how it integrates with the Host, API, Application, and Infrastructure layers.

---

# Core Components

## Correlation Context

Every inbound HTTP request receives a **correlation ID** generated by Frank.Core.  
This ID flows through:

- API request handling  
- Application commands/queries  
- Domain operations  
- Infrastructure persistence  
- Logging and exception boundaries  
- Outbound responses  

Correlation enables **end‑to‑end request tracing** across vertical slices and external integrations.

---

## Request Observation Context

Frank.Core creates a **Request Observation Context** at the start of each request.  
It captures:

- request start time  
- total duration  
- HTTP method and path  
- response status code  
- user ID (if authenticated)  
- exceptions and error boundaries  
- hosting environment metadata  

This context is immutable and flows through the entire request pipeline.

---

## Observation Middleware (Frank.Core)

Two middleware components establish the observability pipeline:

### 1. `InboundObservationContextMiddleware`
Creates the observation context at request start:

- generates or reads correlation ID  
- attaches context to the request  
- begins timing  
- initializes metadata

### 2. `OutboundObservationContextHandler`
Finalizes the observation context:

- stops timing  
- emits final observation event  
- writes `X-Correlation-ID` to the response  
- ensures correlation continuity for clients

These middleware components are **activated by the Host layer**, not the API.

---

# How Observability Works

For each request:

1. **Inbound middleware** creates or reads the correlation ID  
2. Observation context becomes available throughout the request  
3. All logs include the correlation ID automatically  
4. The response includes an `X-Correlation-ID` header  
5. Related requests (e.g., callbacks, retries) share the same correlation ID  
6. The **ErrorBoundaryObserver** captures unhandled exceptions with full context  

This ensures consistent, structured diagnostics across all layers.

# API‑Level Observability

The API layer emits **API‑specific events** using Frank.Core’s observability engine.

### Request Validation Observability

Before an endpoint executes, the API emits:

- `api.validation.start`  
- `api.validation.end`  
- `api.validation.failed`  
- `api.validation.exception`  

These events provide visibility into malformed or invalid client requests and are **activated by the Host layer**.

### Endpoint Execution Observability

Endpoints may emit:

- request‑received events  
- response‑generated events  
- slice‑specific metadata  

All events flow through Frank.Core’s correlation pipeline.

---

# Application‑Level Observability

The Application layer emits events related to:

- command dispatch  
- query execution  
- domain service orchestration  
- application exceptions  
- unit‑of‑work boundaries  

These events help diagnose business‑logic behavior and performance.

---

# Domain‑Level Observability

Domain events may emit observability signals for:

- aggregate operations  
- invariants  
- domain exceptions  
- state transitions  

These events are typically high‑level and business‑focused.

---

# Infrastructure‑Level Observability

Infrastructure emits events for:

- DbContext lifecycle  
- SQL command execution  
- persistence failures  
- external service calls  
- retries and transient faults  

These events help diagnose performance bottlenecks and persistence issues.

---

# Host Layer Responsibilities

The Host layer activates the entire observability pipeline:

```csharp
app.UseFrankCoreApiPlatform();
```

This ensures:

- correlation IDs are generated  
- observation context is created  
- validation observability is active  
- exception boundaries are enforced  
- all layers emit events through the same engine  

The Host layer does **not** define observability events — it only activates the pipeline.

---

# Error Boundary Observer

The **ErrorBoundaryObserver** captures unhandled exceptions with full context:

- correlation ID  
- request metadata  
- stack trace (if enabled)  
- environment metadata  
- exception type and message  

This ensures production diagnostics remain actionable and traceable.

---

# Summary

Observability in Camp Fit Fur Dogs is a **cross‑cutting system** powered by Frank.Core and enriched by product‑specific events from the API, Application, Domain, and Infrastructure layers.

It provides:

- correlation  
- request tracing  
- structured diagnostics  
- validation observability  
- exception boundaries  
- environment‑aware logging  

The Host layer activates the pipeline, while each product layer emits its own domain‑specific events.

This unified model ensures predictable, actionable observability across all environments.
