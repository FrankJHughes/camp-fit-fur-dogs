# Frank.Identity.EntityFrameworkCore — Migrations

The **Migrations** subsystem defines how identity persistence evolves over time. It contains the EF Core migration files, schema evolution rules, and database‑level structural changes required to support Identity domain models such as Users, Sessions, and LockoutState. This layer is **pure infrastructure** — it contains **no identity logic**, **no authentication flows**, and **no session or lockout rules**. Its sole responsibility is to maintain the database schema that the Identity subsystem depends on.

This document describes the Migrations subsystem under:

```
docs/03-frank-identity/entityframeworkcore
```

and maps it back to its implementation in:

```
src/Frank/Identity/EntityFrameworkCore
```

---

## Purpose

The Migrations subsystem exists to:

- define the database schema for identity persistence  
- evolve identity tables and columns as domain models change  
- ensure schema consistency across environments  
- support automated and manual migration workflows  
- keep identity persistence aligned with domain invariants  

Migrations are the history of how identity persistence has changed over time.

---

## Responsibilities of the Subsystem

### Migration Files  
Migration files define schema changes for identity persistence.

Responsibilities:

- create identity tables (Users, Sessions, LockoutState)  
- add or modify columns as domain models evolve  
- enforce database constraints aligned with domain invariants  
- create indexes for identity lookup performance  
- support rollback via `Down` methods  

Migration files are generated by EF Core and refined as needed.

---

### Schema Evolution  
Migrations ensure the identity schema evolves safely.

Responsibilities:

- add new identity fields (e.g., provider metadata, claim storage)  
- update session structures (expiration, revocation markers)  
- update lockout structures (failure counters, timestamps)  
- maintain backward compatibility when possible  
- ensure schema changes do not break existing identity flows  

Schema evolution follows domain changes, not application logic.

---

### Database Constraints  
Migrations enforce constraints that reflect identity domain invariants.

Examples:

- non‑null provider subject  
- unique identity ID  
- valid timestamp ranges  
- required session metadata  
- lockout counters must be non‑negative  

Constraints ensure invalid identity state cannot be persisted.

---

### Indexing Strategy  
Indexes support identity lookup performance.

Examples:

- index on provider subject  
- index on identity ID  
- index on session token  
- index on lockout state identity ID  

Indexes are critical for authentication and session validation performance.

---

### Provider‑Specific Behavior  
Migrations adapt to the configured database provider.

Responsibilities:

- SQL Server / PostgreSQL / SQLite compatibility  
- provider‑specific column types  
- provider‑specific constraints and indexes  
- provider‑specific timestamp handling  

Provider behavior is configured in the DbContext.

---

## How Migrations Connect to the Broader Platform

Identity EF Core migrations collaborate with:

- **Frank.Identity.EntityFrameworkCore**  
  - DbContext uses migrations to build schema  
  - configurations define how domain models map to tables  

- **Frank.Identity.Domain**  
  - domain invariants influence schema constraints  
  - domain model changes drive migration creation  

- **Frank.Identity.Application**  
  - application services rely on persisted identity state  
  - session issuance and lockout evaluation depend on schema correctness  

- **Frank.Core.Infrastructure**  
  - migration tooling (CLI, automated pipelines)  
  - environment detection for dev/prod migration behavior  
  - logging and exception handling  

Migrations ensure identity persistence remains stable and predictable.

## Runtime Collaboration Points

Migrations interact with the runtime by:

- applying schema updates during deployment  
- supporting automated migration execution in CI/CD  
- enabling local development with up‑to‑date identity schema  
- ensuring identity tables remain consistent across environments  
- providing EF‑level logs for observability  

Migrations ensure identity persistence evolves safely.

## Composition Flow (Domain → Configurations → Migrations → Database)

```
Identity Domain Model
    ↓
Entity Configuration (owned types, converters)
    ↓
EF Core Migration Generated
    ↓
Migration Applied to Database
    ↓
IdentityDbContext Uses Updated Schema
```

Migrations are the mechanism that keeps identity persistence aligned with domain evolution.
